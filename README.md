# T08 패스키 포트폴리오 (초보자용 안내)

비밀번호 없이 **패스키(Passkey / WebAuthn)** 로만 로그인하는 개인 공간 데모입니다.
Windows Hello, 휴대폰 지문/얼굴 인식, 보안 키 등으로 로그인하고, 로그인해야만 보이는
비공개(합성) 자료 3건을 확인할 수 있습니다.

## 1. 실행 방법

```bash
npm install
npm run dev
```

브라우저에서 `http://localhost:3000` 을 엽니다.

> **주의**: 패스키(WebAuthn)는 `localhost` 또는 `https` 에서만 동작합니다. 그냥 파일을
> 더블클릭해서 열거나 IP 주소로 접속하면 동작하지 않습니다.

## 2. 사용해보는 순서 (제출문과 동일)

1. 첫 화면 → **"나만의 공간으로 이동"** 클릭
2. 합성(가짜) 이름 입력 → **"패스키 만들기"** 클릭 → Windows Hello 등 인증 창이 뜨면 지문/PIN 등으로 승인
3. 로그인 성공 화면에서 패스키 이름·등록일, 비공개 자료 3건이 보이는지 확인
4. **"다른 기기에서 쓸 패스키 추가"** 로 두 번째 패스키를 등록해서 관리 화면 확인
5. 로그아웃 후 다시 "기존 패스키로 로그인" 으로 재로그인 테스트

## 3. 폴더 구조 (초보자를 위한 설명)

```
src/
  app/
    page.tsx            공개 첫 화면 (로그인 없이 누구나 접속 가능)
    my-space/page.tsx   "나만의 공간" 화면 (등록/로그인/로그아웃/패스키 관리 UI)
    api/                서버 로직 (브라우저가 fetch로 호출하는 API들)
      register/options  패스키 "만들기" 시작 (서버가 challenge 발급)
      register/verify   패스키 "만들기" 완료 검증 + 공개키 저장
      login/options     패스키 "로그인" 시작 (서버가 challenge 발급)
      login/verify      패스키 "로그인" 완료 검증 + 세션 발급
      me                내 정보 + 비공개 자료 조회 (로그인 필요, 없으면 401)
      logout            로그아웃 (서버에 저장된 세션 자체를 삭제)
      passkeys/delete   패스키 삭제 (마지막 1개는 삭제 금지)
  lib/
    db.ts         간단한 파일 기반 데이터베이스 (data/db.json)
    session.ts    로그인 세션 쿠키, CSRF 토큰 처리
    challenge.ts  WebAuthn challenge 저장/1회용 소모 처리
    webauthn.ts   rpID/rpName/origin 설정
    privateData.ts 합성(가짜) 비공개 자료 3건
data/db.json      실제 데이터 저장 위치 (자동 생성됨, git에는 올라가지 않음)
```

## 4. 왜 이렇게 만들었는지 (보안 설계 요약)

| 요구사항 | 어떻게 지켰나 |
|---|---|
| 서버엔 공개키·credential ID·서명 횟수만 저장 | `data/db.json` 의 `passkeys` 에 `publicKey`(공개키), `id`(credential ID), `counter`(서명 횟수)만 저장. 비밀번호·개인키는 애초에 서버로 전송되지 않음 (WebAuthn 표준 동작) |
| 로그인 전 비공개 자료 노출 금지 | `/api/me` 가 세션 쿠키를 확인해 없으면 무조건 401 반환. 첫 화면(`page.tsx`)은 서버 컴포넌트지만 세션 데이터를 아예 조회하지 않음 |
| challenge 재사용 방지 | `lib/challenge.ts` 의 `consumeChallenge()` 가 사용 즉시 DB에서 삭제 (1회용) + 5분 만료 |
| 삭제된 패스키로 로그인 거부 | 로그인 검증 시 매번 DB에서 credential ID로 다시 조회. 삭제되어 없으면 401 |
| 마지막 패스키 삭제 금지 | `/api/passkeys/delete` 에서 본인 소유 패스키가 1개뿐이면 400 에러 반환 |
| 다른 계정 자료 조회 금지 | 항상 "로그인한 세션의 userId" 기준으로만 DB를 필터링. 클라이언트가 보낸 다른 사용자 ID는 절대 신뢰하지 않음 |
| 로그아웃 시 재사용 불가 | 쿠키만 지우는 게 아니라 서버 DB에 저장된 세션 레코드 자체를 삭제 → 예전 쿠키를 다시 보내도 무효 |
| CSRF 방지 | 로그인 시 발급한 `csrfToken` 을 로그아웃/삭제 같은 상태 변경 요청에 `X-CSRF-Token` 헤더로 함께 보내야 통과 |

## 5. 패스키는 어디에 저장되나요?

실제로 등록해보면 운영체제/브라우저가 다음 중 하나를 물어봅니다:

- **이 기기(Windows Hello 등)**: 컴퓨터 자체의 보안 칩에 저장
- **Google 비밀번호 관리자(크롬 계정 동기화)**
- **보안 키(USB 등 물리 장치)**

과제 제출문에는 실제로 선택한 항목을 적어야 합니다.

## 6. 배포하려면 (Vercel 등)

로컬(`localhost`)이 아닌 실제 도메인에 배포할 때는 반드시 환경 변수를 설정해야 합니다.

```
RP_ID=your-domain.vercel.app
ORIGIN=https://your-domain.vercel.app
```

`RP_ID`는 프로토콜(https://) 없이 도메인만, `ORIGIN`은 프로토콜을 포함한 전체 주소를 넣습니다.

## 7. 자동 테스트 (지문 없이 전체 흐름 검증)

사람이 지문/PIN을 직접 누르지 않아도, 크롬의 **가상 인증장치(Virtual Authenticator)**
기능을 이용해 패스키 등록부터 로그인까지 전체 흐름을 자동으로 검증할 수 있습니다.

```bash
npm run dev          # 한 터미널에서 개발 서버 실행
npm run test:e2e     # 다른 터미널에서 자동 테스트 실행
```

`scripts/e2e-passkey-test.mjs` 가 확인하는 17가지 항목:

1. 로그아웃 상태 화면 표시
2. 패스키 등록 성공
3. 로그인 상태 전환 및 이름 표시
4. 비공개 자료 3건 표시
5. 등록된 패스키 개수 표시(1개)
6. 다른 기기로 두 번째 패스키 추가 등록
7. 공개 첫 화면에는 비공개 자료/이름이 노출되지 않음 (+200 OK로 열림)
8. 로그인 전 `/api/me` 401 반환
9. 패스키가 2개 이상일 때 삭제 허용
10. 마지막 남은 패스키 삭제 거부 (400)
11. CSRF 토큰 없는 로그아웃 거부 (403)
12. 정상 로그아웃 성공
13. 로그아웃 후 같은 쿠키로 재접근 불가 (401, 서버 세션 완전 삭제 확인)
14~16. 남은 패스키로 재로그인 성공 및 데이터 일관성 확인

가장 최근 실행 결과: **17개 중 17개 통과**.

## 8. 알아두면 좋은 한계점

- `data/db.json` 은 배우기 쉽도록 만든 **파일 기반** 저장소입니다. Vercel 같은 서버리스
  환경에 배포하면 재배포/재시작 시 데이터가 초기화될 수 있습니다. 실제 서비스라면
  Postgres, SQLite(파일 유지되는 서버), Redis 등으로 바꿔야 합니다.
- 위 자동 테스트는 가상 인증장치를 쓰므로, 실제 지문 센서·Windows Hello 화면이 뜨는지
  같은 "사람 눈에 보이는 UX"까지 보장하진 않습니다. 최종 제출 전에는 실제 브라우저에서
  한 번쯤 손으로도 눌러보는 것을 권장합니다.
